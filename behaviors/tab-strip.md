# Tab strip — the label clamp and the trailing chrome

The strip is the row every tab shares, so one tab's appetite is every other
tab's reachability. Two behaviors live here: a bound on how much of the strip
a single name may take, and the trailing buttons that act on the focused pane
without a keyboard. Both were asked for by the user on 2026-08-20 ("tab name
alanı maks 20 karakter görünsün — alanı rahat kullanamıyorum" · "+ butonunun
sağına split down / split right butonları"); design notes:
`.local/prd/session-29-usability-wave.md` §2.

| ID | Behavior | What breaks if it is lost | Verified by |
|---|---|---|---|
| TP-TAB-NAME-01 | A tab's NAME paints at most twenty display cells, cut with an ellipsis, measured in cells not characters. The clamp runs on the name alone, before the unseen dot and the zoom suffix are attached, and inside `tab_chrome_label` — the one seam `tab_width`, the hit areas and the paint all read. | A single long name widens its tab until the neighbours scroll out of reach — the reported complaint. Clamping anywhere but the shared label seam would let the painted text, the measured width and the pressable cells disagree; clamping after the marks would let a long name swallow the unseen dot or the zoom suffix, which are state channels, not decoration. | `a_long_tab_name_is_clamped_to_twenty_cells`, `a_name_exactly_at_the_limit_is_untouched`, `a_name_under_the_limit_is_untouched`, `the_unseen_and_zoom_marks_survive_the_clamp`, `the_clamp_measures_display_cells_not_chars` |
| TP-TAB-SPLIT-01 | The two three-cell split buttons — right split, then down split ending at the edge — are pinned flush to the strip's far right, while the `+` keeps trailing the tabs. Their seats are carved out before the tab layout runs (the stage-tab precedent, TP-FTAB-ENTRY-05) and a seat is taken only when the carving leaves the tab layout byte-identical, shrinking tier by tier: both buttons, the right one alone, none. In overflow they are part of the reserved trailing chrome, so they stay reachable however many tabs there are. Whole width or nothing per seat. Keyboard-driven strips (no mouse chrome) carry none of this. | The user asked for a fixed target: buttons that trailed the `+` drifted with every new tab, defeating muscle memory — the reported complaint. A reservation allowed to squeeze the tabs would trade tab visibility for chrome; a partial button paints blank cells that still answer a press — an invisible control (TP-MOD-35's rule, restated for the strip). | `the_split_buttons_stand_pinned_at_the_strip_far_right`, `adding_a_tab_moves_the_plus_but_not_the_split_buttons`, `a_strip_with_exactly_six_spare_cells_seats_both_buttons`, `in_overflow_the_split_buttons_hug_the_right_edge`, `without_mouse_chrome_the_split_buttons_claim_nothing`, `a_strip_too_narrow_for_the_split_buttons_claims_nothing`, `a_strip_with_exactly_three_spare_cells_seats_the_right_button_alone` |
| TP-TAB-SPLIT-02 | A press on a split button resolves to `MouseAction::SplitFocusedPane` with that button's direction and rides the same api road the keyboard split takes; the `+` press beside them still means new tab. | A second split road would be one more place for the split semantics to drift; a swallowed `+` would trade an old control for a new one instead of adding it. | `a_click_on_a_split_button_asks_for_that_direction`, `the_new_tab_button_still_makes_a_tab_beside_the_split_buttons` |
| TP-TAB-BROWSER-01 | A third three-cell button — the browser button — joins the pinned block at the strip's far right, seated LEFT of the split pair so the down split still ends at the edge. Seats are handed out tier by tier from the edge inward: nine spare cells seat all three, six seat the split pair alone, three seat the right split alone; the browser seat is the first one given up. The seat is carved out before the tab layout runs (the split-button precedent) and taken only when the carving leaves the tab layout byte-identical. In overflow it is part of the reserved trailing chrome. Keyboard-driven strips carry none of it. | The user asked for a browser button beside the split buttons. Seating it inside the pair would move cells muscle memory already owns (the reported complaint that pinned the pair in the first place); seating it outside the tiers would let it squeeze the tabs on a narrow strip. Giving it up first keeps the older controls where they always were. | `the_browser_button_stands_left_of_the_split_pair`, `a_strip_with_exactly_nine_spare_cells_seats_all_three_buttons`, `a_strip_with_six_spare_cells_gives_the_browser_button_up_first`, `the_browser_button_follows_the_split_pair_in_overflow_and_absence` |
| TP-TAB-BROWSER-02 | A press on the browser button resolves to `MouseAction::OpenWebPane` and rides `pane.web.open` — the one api road every browser button, key and CLI verb takes — which births a pane beside the target running `command` (default `terminal-browser open <url>`) with `HERDR_WEB_PANE=1` in its environment; the split pair beside it keeps meaning split. | A second road to a browser pane would be one more place for its semantics to drift (TP-TAB-SPLIT-02's rule, restated); `pane.split` cannot birth a pane running a program, so the road is its own method rather than a flag on the split. | `a_click_on_the_browser_button_asks_for_a_web_pane`, `pane_web_open_births_a_pane_running_the_command_beside_the_target`, `open_web_pane_key_asks_for_a_web_pane_on_both_roads`, `parse_pane_web_open_args_accepts_url_ratio_and_command`, `spec_includes_pane_web_open`, `web_config_names_the_browser_and_defaults_to_terminal_browser`, `pane_web_open_runs_the_configured_browser_when_no_command_is_given`, `headless_deferred_web_pane_request_births_a_browser_pane` |
| TP-TAB-BROWSER-03 | The browser button's label follows the icon profile — the codicon browser glyph in the Nerd profile, a plain `w` in the ASCII profile — and fills its three-cell seat exactly in either. | A glyph wider than one cell would spill into the split pair's cells; a font-bound glyph with no fallback would paint a tofu box on a host without the font, and the visual fixtures run in the ASCII profile precisely so their digests do not depend on a font. | `the_browser_label_fills_its_seat_in_both_profiles` |
