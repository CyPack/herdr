# Surface chrome — edge bars, framed panels and boxed controls

This fork lets a person decide which of herdr's surfaces wear a frame, what
colour it is, and whether the panel's own controls are drawn as boxed buttons.
Upstream has none of it: every one of these behaviors is ours to lose.

All of it is **off by default**. A frame costs two cells on each axis of a
surface that is often already the narrowest one on screen, so turning one on is
a composition choice rather than a restyle — and the default path still draws
what it drew before, which is what keeps this work inside `V1.x` of
`docs/superpowers/specs/2026-07-19-herdr-files-layout-v1-lock.md`.

Design rationale and the measurements behind each decision:
`.local/prd/custom-layout-v2.md` (§9 bars, §11 chrome).

## Edge bars — `[shell.bars.<edge>]`

| ID | Behavior | What breaks if it is lost | Verified by |
|---|---|---|---|
| TP-CHROME-01 | With no `[shell.bars]` table, the derived tree is structurally identical to the one herdr has always drawn | Everyone pays for a feature they did not ask for, and every visual baseline moves in a single commit | `no_configured_bar_derives_exactly_todays_tree` |
| TP-CHROME-02 | Each of the four edges can carry a bar on its own (`top`→TopBar, `bottom`→BottomBar, `left`→AppDock, `right`→RightPanel) | "A bar on whichever side you want" is the whole request; region ids already existed and none were invented | `each_edge_can_carry_a_bar_by_itself` |
| TP-CHROME-03 | All four bars at once still leave a workspace stage | Bars could eat the surface the app exists to show | `all_four_bars_at_once_still_leave_a_stage` |
| TP-CHROME-04 | A size outside 1..32 is refused with a warning rather than clamped | Silently resizing someone's number hides their mistake behind a layout they did not write | `an_impossible_bar_size_is_refused_rather_than_repaired` |
| TP-CHROME-05 | A bordered bar thinner than three cells is refused, not drawn borderless | A bare band where a frame was asked for reads as the border failing, not as the size being impossible | `a_bordered_bar_thinner_than_its_border_is_refused` |
| TP-CHROME-06 | Every enabled-edge composition carries its own revision, and the exact composition is in the geometry key | Two different screens answering to one identity is CLA3: the cache returns the old geometry and hit testing goes to the wrong region | `every_edge_composition_has_its_own_revision` |
| TP-CHROME-07 | A composition that fails validation falls back to the legacy tree instead of propagating an error | A shell that cannot be composed must still show a shell; config is untrusted input | `a_bar_composition_that_does_not_validate_falls_back_to_the_legacy_tree` |

## Bar sections — `[[shell.bars.<edge>.sections]]`

A bar can be divided into at most eight parts along its long axis. A section is
an address: what fills it and what a click on it does are answered by later
layers, and the number it was written at is the only stable name it has.

| ID | Behavior | What breaks if it is lost | Verified by |
|---|---|---|---|
| TP-CHROME-23 | More sections than a bar may hold leaves it undivided with a warning, rather than keeping the first eight | Truncation hands someone a layout they did not write and renumbers every section after the one that vanished | `a_bar_refuses_a_ninth_section_rather_than_dropping_it` |
| TP-CHROME-24 | Exactly the maximum number of sections is accepted | A ceiling that cannot be reached is an off-by-one that silently destroys a section | `a_bar_accepts_exactly_its_maximum_number_of_sections` |
| TP-CHROME-25 | Section widths come from the shell solver's own three phases, including its largest-remainder tie-break | A second distribution implementation drifts by one cell the first time two remainders tie, and both answers stay internally consistent | `section_widths_come_from_the_shell_solvers_own_arithmetic`, `an_odd_remainder_goes_to_the_earlier_section_every_time` |
| TP-CHROME-26 | A top or bottom bar is divided across its width; a left or right bar down its height | The wrong axis collapses every section onto the same cells and still looks plausible | `a_side_bar_divides_its_height_and_an_edge_bar_divides_its_width` |
| TP-CHROME-27 | Sections account for the bar's content area exactly, and stay inside its border | A short division leaves an undrawn strip; a long one writes into the region next door; either escapes the frame it was promised | `sections_fill_the_bar_exactly_without_overrunning_it`, `sections_of_a_bordered_bar_stay_inside_its_border` |
| TP-CHROME-28 | A section squeezed to no cells is not a target | A zero-width rectangle that still answers clicks answers for its neighbour | `a_section_squeezed_to_nothing_is_not_reported_as_occupied` |
| TP-CHROME-29 | A section is clicked exactly where it is drawn, framed or not, and only against the generation that drew it | This is the fourth place the same defect could appear: drawing reads the live value, hit testing is handed a constant, and both rectangles stay plausible | `every_bar_section_is_clicked_exactly_where_it_is_drawn`, `a_bar_section_answers_only_for_the_generation_that_drew_it` |
| TP-CHROME-30 | A different division is a different geometry identity, and re-dividing advances the generation exactly once | Same key means the cache returns the previous rectangles and every click in that bar answers for the wrong section | `changing_only_a_sections_policy_changes_the_bars_identity`, `redividing_a_bar_misses_the_cache_and_advances_the_generation_once` |
| TP-CHROME-31 | One unreadable section leaves the whole bar undivided rather than dropping just that entry | Dropping one entry shifts every later index, silently moving whatever those indices address | `an_unreadable_section_leaves_the_bar_undivided_rather_than_renumbered`, `a_section_with_impossible_numbers_is_refused` |
| TP-CHROME-32 | A sections array survives the live config reader, not just the model | The layer that added `[shell.bars]` tested the model and never a file; a dropped array reloads as an undivided bar while the file plainly says otherwise | `a_bars_sections_array_survives_the_live_reader` |
| TP-CHROME-33 | An undivided bar projects no section targets at all, and is still a target itself | Everyone who never divides a bar must pay nothing for the feature | `an_undivided_bar_contributes_no_section_hits`, `a_bar_without_sections_divides_into_nothing` |
| TP-CHROME-34 | A component placement naming a region the tree does not contain is refused | Such a placement draws nothing and reports nothing; the gate is the only place that can notice | `shell_rejects_a_placement_whose_region_is_not_in_the_tree` |
| TP-CHROME-35 | A bar setting this build refuses is reported by `herdr config check`, naming the key, the value, the rule and the consequence — and a section's complaint names its index | Parsing only sees keys it does not recognise; a correctly spelled key holding an undrawable value used to be answered "ok", sending the person to look at their terminal instead of the line they wrote | `an_out_of_range_bar_size_is_reported_with_its_edge`, `a_bordered_bar_too_thin_reads_differently_from_one_out_of_range`, `an_unknown_section_kind_is_reported_with_its_index`, `an_impossible_content_section_and_too_many_sections_are_reported` |
| TP-CHROME-36 | What the checker reports and what the deriver refuses come from one predicate, proven equivalent across every case in both directions | Two copies of the same range rules agree the day they are written and drift on the first change to either, and neither side goes red because each stays internally consistent | `every_reported_problem_is_a_bar_that_is_actually_refused`, `a_drawable_configuration_produces_no_complaints` |
| TP-CHROME-37 | A section's click action is resolved at the index that section was written at, with its command carried through exactly | An action that lands one index over runs somebody's command from the wrong part of the bar, and both parts still look right | `a_section_action_answers_at_the_index_it_was_written_at`, `a_press_resolves_the_action_of_the_section_it_landed_in` |
| TP-CHROME-38 | Every edge resolves its actions through the same region mapping its track is drawn from, and a region that is not an edge bar resolves none | The left bar lives in the dock's region; a second copy of that mapping runs the right bar's command for a click on the left one | `each_edge_s_actions_answer_at_the_region_its_track_is_drawn_in` |
| TP-CHROME-39 | A division that was refused leaves no addressable actions behind | Actions are addressed by section index; a list that outlived its sections runs the command of a part that is not on screen | `a_refused_division_leaves_no_addressable_actions` |
| TP-CHROME-40 | An action this build cannot run costs only its own section — the division stands, the indices do not shift, and `herdr config check` names it | Taking a whole bar's layout down for a misspelled command is disproportionate; silently dropping the entry would renumber everything after it | `an_unusable_action_costs_only_the_section_that_carries_it`, `config_check_reports_an_action_this_build_cannot_run` |
| TP-CHROME-41 | A press over a section resolves only against the generation that drew it | Coordinates from a layout that no longer exists would run a command from whatever now sits under them | `a_press_from_a_vanished_generation_runs_nothing` |
| TP-CHROME-42 | A bar press while a popup is open opens no second popup and closes no first one, and says why | Dropping somebody's open work on a stray bar click is not undoable | `a_press_while_a_popup_is_open_neither_opens_nor_closes_one`, `a_second_popup_is_refused_without_touching_the_first` |
| TP-CHROME-43 | Every event over a section stops at the bar — including a section with no action — while a press elsewhere in the bar, and any in-flight gesture, is left alone | An event falling through chrome acts on the surface behind it; claiming a drag mid-flight strands a gesture that already had an owner | `every_event_over_a_section_stops_at_the_bar` |
| TP-CHROME-44 | An action that cannot be started says so and leaves nothing behind | A bar that silently does nothing when clicked reads as broken chrome, and the person has no way to learn why | `a_section_action_that_cannot_run_says_so_and_opens_nothing` |
| TP-CHROME-45 | A section's popup opens at the size that section asked for, in cells or percent, carried unresolved from config through the click and into the popup that opens | A size dropped at any hop looks exactly like the default, so the failure is invisible; resolving it early would need a geometry the derivation has never seen. The last hop needed its own test: a mutation that dropped the size at the spawn call left every other test green | `a_popup_action_carries_the_size_it_was_written_with`, `a_press_carries_the_popup_size_the_person_asked_for`, `a_sized_section_opens_its_popup_at_the_size_it_asked_for` |
| TP-CHROME-46 | A popup size on a section that opens no popup is reported, and the derived action carries no size either — while an unreadable action kind reports only its own cause | A size that can never take effect reads as one that does; two complaints for one mistake send somebody to fix the wrong line | `a_popup_size_on_something_that_is_not_a_popup_is_reported`, `a_reported_leftover_size_is_a_size_the_action_does_not_carry` |
| TP-CHROME-47 | Changing only a popup's size leaves the bars' geometry identity untouched | A command's size decides nothing about where a rectangle is; keying on it would invalidate every cached rectangle on screen for a change that moves nothing | `changing_only_a_popup_size_leaves_the_bars_identity_alone` |
| TP-CHROME-48 | A size larger than the screen is clamped inside it, and an area with no room for a popup is refused rather than squeezed | This resolver now takes numbers from a config file, not only from a keybind somebody typed; both ends of the range are reachable by accident | `an_absurd_size_is_clamped_and_a_hopeless_area_is_refused` |
| TP-CHROME-49 | The first press outside a popup delivers Esc into the program and does NOT close the pane | Editors bind Esc to save-then-quit; taking the pane away races their final write. This behaviour existed with no test and no entry, so the escape hatch built on top of it could have removed it with nothing going red | `a_first_press_outside_a_popup_asks_it_to_quit_rather_than_killing_it` |
| TP-CHROME-50 | A second press outside closes a popup that ignored the first, and the request is remembered against that popup's own terminal so a later popup can never inherit it | btop and htop quit on `q` and ignore Esc, so without an escalation the surface is stuck; a bare flag would let one popup's dismissal be spent on its successor | `a_second_press_outside_closes_a_popup_that_ignored_the_first` |
| TP-CHROME-52 | A section's label is emitted, addressed AND painted, inside that section's own rectangle | A widget that is derived, given a rectangle and never drawn passes every state test and the compiler counts it as used, because it is — just not by anything that paints. Only a buffer dump separates those, and this fork lost a sidebar row for a release to exactly that | `a_section_label_is_painted_inside_its_own_section_and_clipped_by_display_width` |
| TP-CHROME-53 | A label is clipped by display width, and never changes how wide its section is | An emoji is two cells, so clipping by character count paints over the neighbour; and letting text size a section would put that text in the geometry key, re-laying-out the bar for a change that moves nothing | `a_section_label_is_painted_inside_its_own_section_and_clipped_by_display_width`, `a_widget_this_build_cannot_show_is_reported_and_never_reaches_the_geometry` |
| TP-CHROME-54 | A widget this build cannot show, and text with no widget to show it, are both reported — and neither is carried into the derived chrome | Text that will never appear reads exactly like text that will; the checker and the deriver stay joined so one cannot say yes while the other says no | `a_widget_this_build_cannot_show_is_reported_and_never_reaches_the_geometry` |
| TP-CHROME-55 | A section's label is drawn in a colour that differs from the background of the cell it lands in | This fork shipped a label whose foreground was `panel_contrast_fg`, which returns the panel background — the very surface the bar had just been painted with. Every state test passed, the glyph dump passed, and the user saw a bordered bar with nothing in it. A character-only assertion cannot tell "painted" from "painted invisibly", so legibility needs a claim of its own | `a_section_label_is_painted_in_a_colour_you_can_see_against_its_own_surface` |
| TP-RES-01 | The aggregate `cpu` line of `/proc/stat` is summed rather than indexed, and `cpu0` is never mistaken for it | The field count has grown across kernel releases, so a fixed arity silently reads the wrong columns on a newer machine; and matching the prefix alone reads one core and calls it the machine | `the_aggregate_cpu_line_is_summed_including_fields_added_by_newer_kernels`, `the_per_core_lines_are_not_mistaken_for_the_aggregate` |
| TP-RES-02 | A percentage comes from the difference between two readings, and two readings that cannot produce one refuse rather than divide | The kernel exposes time since boot, so one reading describes the machine's whole uptime; and equal or backwards counters — which a suspend produces — would divide by zero or report a negative busy share | `a_percentage_is_the_busy_share_of_the_interval_between_two_readings`, `two_readings_that_cannot_produce_an_answer_refuse_instead_of_dividing`, `the_first_reading_leaves_the_percentage_unknown_rather_than_inventing_zero` |
| TP-RES-03 | Memory used is derived from `MemAvailable`, not `MemFree`, and kB become bytes | Free memory on a healthy Linux box is near zero because the kernel spends it on cache, so a meter built on `MemFree` reads ~97% used while idle and teaches its owner to ignore it | `memory_is_derived_from_available_rather_than_free_and_kb_become_bytes` |
| TP-RES-04 | A counter that could not be read renders `--`, a pool the machine does not have renders `off`, and neither ever renders a zero | A silent zero is indistinguishable from an idle machine, so a broken meter reads as a working one; and collapsing "absent" into "unreadable" tells somebody with no swap that their meter is broken | `a_reading_that_failed_shows_dashes_and_never_a_zero`, `a_machine_with_no_swap_says_so_rather_than_looking_broken` |
| TP-RES-05 | Reading the files is separated from the arithmetic over them | A parser holding its own file handle can only be tested on a machine that has the file, which is exactly the machine where the mistakes are hardest to see | `the_aggregate_cpu_line_is_summed_including_fields_added_by_newer_kernels`, `a_truncated_or_unreadable_stat_refuses_rather_than_guessing` |
| TP-RES-06 | A platform with no reader reports nothing rather than zero | Only Linux has a reader; macOS and Windows must show `--` rather than a fabricated idle machine, and that path is the same one a Linux box with an unreadable `/proc` takes | `a_reading_that_failed_shows_dashes_and_never_a_zero` |
| TP-RES-07 | Sampling is demand-driven: with no live section configured, nothing is read and no wakeup is asked for | Sampling always and discarding the answer would make every herdr on every machine pay for a widget almost nobody turns on | `a_bar_with_no_live_section_never_reads_the_machine_and_asks_for_no_wakeup` |
| TP-RES-08 | Whether a reading is due is decided against the `now` the caller passes, never against a clock read inside the check | A deadline getter that called `Instant::now()` itself made the first reading due at a moment already past by the time the caller compared against it, so it never fired at all — caught by the interval test, invisible to every other one | `the_loop_reads_the_machine_once_per_interval_and_not_per_call` |
| TP-RES-09 | Drawing never reads the machine; the loop reads it, once per interval | A sampler called from render looks identical on screen and costs a `/proc` open per frame. Only counting reads across many frames separates the two | `drawing_a_live_section_many_times_never_reads_the_machine`, `the_loop_reads_the_machine_once_per_interval_and_not_per_call` |
| TP-RES-10 | What a live section paints comes from the sample held in state, not from a default | Dropping the last hop is invisible: a default formats as `--`, which is exactly what an unreadable machine paints, so the screen and every other test go on looking correct. A mutation swapping the sample for `Default` left the whole suite green until this test existed | `a_live_section_paints_the_sample_that_is_in_state_rather_than_a_default` |
| TP-CHROME-56 | A `resource` widget naming a metric this build does not know is refused, with its own message | A metric typo that renders as an empty section is indistinguishable from a section meant to be empty; and folding it into the unknown-kind message would send somebody to fix the wrong line | `a_resource_widget_with_an_unknown_metric_is_reported_and_never_reaches_the_geometry` |
| TP-CHROME-51 | Only a press arms the dismissal, and a press back inside the popup cancels one it never answered | Crossing the background with a pointer is not intent; and Esc may have opened an "unsaved changes?" prompt whose answer lands inside, so closing on the next outside press would drop the very question the guarantee protects | `moving_past_a_popup_does_not_arm_its_dismissal`, `returning_to_the_popup_cancels_a_dismissal_it_did_not_answer` |

## The rule this family keeps learning

A shared geometry function is not shared if one caller hands it a constant.
Three separate controls in this fork recomputed the panel's rectangles from
`SidebarChrome::NONE` while the renderer used the live value, and none of them
produced a red test. When a context argument is added to a geometry helper, its
call sites get grepped for constants before the change is called done.
