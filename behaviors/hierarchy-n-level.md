# N-level node tree — registered behaviors

The generalisation of the four-level tree: `[[spaces.node]]` containers hang
under each other by `parent`, split rules hang their buckets under nodes, and
yesterday's `[[spaces.project]]` is the depth-one case — a parentless node.
Assignment stays config-authored and render-time resolved; nothing about the
tree shape is ever persisted except the per-display folds.

Format and rules: [`README.md`](README.md).

## Model

| ID | Behavior | Breaks if lost | Verified by |
|---|---|---|---|
| TP-NODE-01 | An absent `[[spaces.node]]` table produces no nodes: the feature is opt-in and an untouched config renders exactly as before. | Every existing sidebar changes shape on update — the additive contract of the whole spaces family breaks. | `an_absent_node_table_produces_no_nodes` |
| TP-NODE-02 | A `[[spaces.project]]` doubles as a parentless node — and may carry a `parent` itself, so the sugar is complete. | Projects and nodes become two vocabularies; the tree walker forks and the two halves drift. | `a_project_entry_may_carry_a_parent_too` |
| TP-NODE-03 | Tree-shape problems (cycles, unknown parents, depth past eight) degrade to a flatter tree plus a diagnostic — never a failed load, never a hung walker. | One typo in a parent chain takes the whole sidebar down, or worse, spins the emitter forever. | `a_cycle_is_reported_and_its_nodes_go_top_level` |

## Emission

| ID | Behavior | Breaks if lost | Verified by |
|---|---|---|---|
| TP-NODE-04 | The chain reads top-down and order stays order-by-first-member, recursively: every ancestor header appears before its children, where the subtree's first member sits in workspace order. | Headers appear after or away from their content and the drawer's spatial memory — built on workspace order — dies. | `nested_nodes_emit_parent_before_child_before_the_bucket` |
| TP-NODE-05 | A parented bucket with one member elides its header: the checkout hangs straight under the node, indented. | "Move this branch under X" draws a one-member bucket ceremony instead of the branch simply sitting under X. | `a_single_member_parented_bucket_hangs_its_member_under_the_node` |
| TP-NODE-08 | A module bucket is a parent like any other: a node whose parent is a split rule's key is a valid tree, every chain walker (depth, climb, chain-hit) crosses bucket edges, and a defined rule key is never a "ghost parent". | Modules refuse to hang under buckets, or mixed chains stop halfway up and draw at the wrong depth or under the wrong root. | `a_node_may_hang_under_a_bucket`, `node_depth_walks_through_buckets` |
| TP-NODE-09 | A cycle that runs through a bucket is still a cycle: the validator walks bucket edges too, reports it, and drops the node side to top level. | A loop with one rule-edge slips past validation and hands the sidebar walker an infinite chain. | `a_cycle_through_a_bucket_is_still_caught` |
| TP-TREE-16 | A node under a bucket is drawn inside that bucket's block, pre-order — the bucket's own members lead, then the child module, then that module's buckets. | TP-TREE-17 | Folding a bucket hides the modules (and their buckets) hanging under it, exactly as it hides its member checkouts. | A folded bucket keeps leaking its subtree below itself. | `a_folded_bucket_hides_the_modules_under_it` |
| TP-MOD-13 | A container declared at top level takes a row even though no checkout climbs to it. | The tree is walked from the checkouts up, so a container nothing hangs under is never reached — and naming the module before making the branch is the first thing a person does. | `a_top_level_module_with_no_members_still_takes_a_row` |
| TP-MOD-14 | Declared containers are drawn after the rows the checkouts produced. | Creating a module pushes the work in progress down the list every time. | `declared_containers_follow_the_rows_the_workspaces_produced` |

| TP-MOD-16 | An all-empty chain is drawn whole, parent before child. | Scaffolding cannot be built top-down: the middle of a chain vanishes and the tree reads as broken. | `a_chain_of_empty_modules_is_drawn_in_order` |
| TP-MOD-17 | A container reachable from both a checkout's climb and the declared forest is drawn once. | Two sources feeding one list draw the same subtree twice. | `a_container_reachable_from_both_sources_is_drawn_once` |
| TP-MOD-18 | A tree with no declared containers emits exactly the rows it emitted before the second source existed. | The second source changes the list for everyone who never uses modules. | `a_tree_without_containers_is_unchanged` |
| TP-MOD-19 | Folding a declared container hides its declared children, as folding hides members. | The fold contract holds for one source and leaks for the other. | `folding_a_declared_module_hides_its_declared_children` |
| TP-MOD-03 | A drawn container with nothing beneath it writes `(no branches yet)` on a row of its own, indented one step past its header, dim. | An empty gap under a header is indistinguishable from damage. The reader cannot tell "nothing here yet" from "the tree broke", and goes hand-editing a working config. | `an_empty_module_says_it_is_empty` |
| TP-MOD-24 | A folded container writes no note: the emission sits after the fold check, not before it. | Describing the inside of a closed box undoes closing it, and folding would change the row count in the wrong direction. | `a_folded_empty_module_writes_no_note` |
| TP-MOD-21 | A module carrying only a rule nobody joined is empty and says so. `buckets_of_node` is derived from the members map, so a memberless bucket is not a child of anything in the drawn tree — the two child maps therefore answer the drawn question directly, with no deeper walk. | Asking a bucket whether it draws anything reads as a guard and is unreachable: every bucket that can appear in the map already has a member. | TP-MOD-22 | A container holding another container is not empty; only the childless one at the bottom writes the note. | A note on a populated parent teaches the reader that the note means nothing, and the honest ones stop being read. | `a_module_that_carries_a_module_is_not_empty_but_its_child_is` |
| TP-MOD-23 | A container over a bucket with members writes no note. | A false note hangs a line of noise under every working module in the tree. | `a_module_over_a_populated_bucket_writes_no_note` |
| TP-MOD-25 | The note is laid out into a vector of its own so it is painted, and into none of the vectors a press resolves against, so it is inert. | Without the rect it is emitted, takes its line, and is never drawn — leaving exactly the gap it exists to explain (the shape that cost the "older chats" row a release). | TP-MOD-08 | A module the machine wrote offers `Delete module` in its own menu, last, after the fold verb. | Creating a module is two clicks; taking one back was a hand-edit of `spaces.managed.toml`, a file the person who clicked has no reason to know exists. | `a_managed_module_offers_to_be_deleted` |
| TP-MOD-26 | A module written by hand into `config.toml` does not offer the verb. | TP-MOD-30 | Children of a deleted container are re-seated at top level with a diagnostic, never dropped. | Silent disappearance reads as data loss to someone who only meant to drop a container. | `a_module_whose_parent_was_deleted_is_re_seated_at_top_level` |
| TP-MOD-09 | A module's row paints its name: the header renderer resolves a row's key against both container tables, not projects alone. | The row is laid out, takes its line, and paints nothing — a blank gap where the module the user just named should be. | TP-MOD-10 | A module's row steps in once per ancestor, measured from the node chain rather than from a member. | A sub-module and a parallel module draw identical rows, so the two creation roads become indistinguishable and "make this a sub-module" has no visible result. | TP-MOD-11 | A folded module wears the disclosure arrow and prints no aggregate state dot. | A module holds no membership of its own, so a dot there summarises nothing and invents a status the tree cannot back. | `a_folded_module_shows_the_arrow_and_no_invented_state_dot` |
| TP-MOD-12 | A project header keeps its arrow, its own icon, its name and its left-edge position after the renderer learned a second identity. | Opening the painter to modules quietly changes what projects have always drawn. | `a_project_header_still_draws_its_arrow_icon_and_name` |
| TP-MOD-01 | A module with no members yet still takes a row under its drawn parent, after the parent's populated buckets. | Making a module produces nothing on screen, so a tree cannot be built before its branches exist — the person names a module, sees no change, and makes a second one with a different name.
